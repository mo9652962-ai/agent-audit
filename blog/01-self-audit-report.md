# 我给自己的 AI Agent 环境做了次安全审计：8 个高危端口报警，最后只有 2 个是真的

> agent-audit 系列第 1 篇。记录一次 Windows 11 本机 agent 环境的完整审计：8 个红色报警怎么变成 2 个真问题、113 处明文密钥为什么先别慌、以及一个和手工审计互相印证的好消息。
>
> 工具已开源：[github.com/mo9652962-ai/agent-audit](https://github.com/mo9652962-ai/agent-audit)

## 三个数字，说明 2026 年的本机 agent 环境已经不安全了

- **800+**：ClawHavoc 供应链投毒顶峰期泛滥的恶意 skill 数量（2026-02）；
- **85%**：国家应急中心通报的、把管理端口监听在 `0.0.0.0` 从而暴露公网的 OpenClaw 实例比例；
- **13.4% / 36.8%**：Snyk 审计 ClawHub 3984 个技能中含严重安全问题和存在漏洞的比例。

这些数字的共同点是：**攻击发生在你自己的机器上**。市场导入的 skill 拥有和你同等的执行权限——terminal、文件系统、网络，一个都不缺。而大多数人对 agent 安全的讨论还停留在 prompt injection 和提示词加固，很少有人回头检查：我这台跑着 agent 的机器，到底向谁敞开了什么？

## 盲区：没人在看自己的机器

我日常跑一套本机 agent 环境（Hermes，207 个 skill，7 个 MCP server），加上 ComfyUI、各类模型服务。这也是大多数 agent 重度用户的典型形态：**一个装满第三方 skill 的执行环境 + 一堆监听端口的服务 + 一目录的 API key**。

于是我把过去几个月沉淀的审计流程做成了一个开源 CLI（`agent-audit`），跑了一次完整审计。7 项检查全部只读：端口暴露、skill 来源分类、外发端点白名单、凭据权限与明文、git 泄漏、依赖漏洞、MCP server 审计。

结果有意思的地方在于：**它先把我吓了一跳，再教了我一课。**

## 第一轮：8 个高危端口报警，一半是误报

报告第一版，端口检查标红了 8 个监听 `0.0.0.0` 的服务。逐条看进程：

```
[high] 0.0.0.0:1053   PID 7928  FlClashCore.exe    ← 真问题
[high] 0.0.0.0:27036  PID 25188 steam.exe          ← 真问题
[high] 0.0.0.0:49664  PID 1788  lsass.exe          ← Windows RPC 动态端口，正常
[high] 0.0.0.0:49665  PID 1620  wininit.exe        ← 同上
[high] 0.0.0.0:49666  PID 2692  svchost.exe        ← 同上
...（spoolsv / services，同理）
```

lsass、svchost 这些 Windows 系统进程监听 `0.0.0.0` 的 49152+ 端口，是 RPC 动态端口的默认行为，不是问题——**但报告把它们和真问题混在了一起**。这就是安全工具的第一课：噪音淹没信号，等于没有信号。我把"系统进程 + 动态端口范围"的判定加进降噪规则后重跑，剩下 2 条，条条是货：

1. **FlClashCore.exe 监听 `0.0.0.0:1053`**——这是代理工具的 DNS 端口，对局域网开放意味着同网段设备（比如连了同一 Wi-Fi 的手机）都能把它的 DNS 当作解析入口。个人电脑上没这个需求，改成只监听 `127.0.0.1` 即可。
2. **steam.exe 监听 `0.0.0.0:27036`**——Steam 串流功能，同理：不用远程串流就在设置里关掉，或防火墙拦掉公网入口。

这两个都不是"黑客工具"，恰恰是这种**正常的、甚至知名的服务**构成了最大的暴露面——因为没人怀疑它们。

## 113 处明文密钥：先别急着删

凭据检查报出 113 处明文密钥命中。这个数字听起来吓人，但要先讲清楚一个常被搞错的区别：

- **`config.yaml` 里有真实 key ≠ 事故**。它是 provider 配置的本职工作，关键问题只有一个：这个文件会不会被带出这台机器？（git 追踪？随配置目录外传？）
- **记忆/文档文件里有真实 key = 事故**。`MEMORY.md` 这类文件天生会被同步、被引用、被塞进上下文——它们只应该放"密钥在 config.yaml 里"这样的位置说明，而不是密钥本身。

我的 113 处命中里，前者占大头（正常配置，配合 git 泄漏检查确认未被追踪即可），后者是需要真正动手清理的。逐条的证据列是 `文件名:行号 → sk-abcde…mnop` 这样的打码形式，修复动作跟着证据走。

顺带一提，`.env` 和 `auth.json` 这类文件**天生就是密钥载体**，扫它们的明文没有意义——该查的是权限：Windows 上用 `icacls` 确认只有当前用户可读（`/inheritance:r` 收紧），Vidar 窃密木马变种就是专偷 agent 配置目录的。

## 26 个市场 skill 与 275 个端点：数量不是证据

207 个 skill 里，26 个来自市场导入（`@` 前缀），181 个官方/自建。外发端点扫描共扫了 919 个文件，第一轮报出 691 处"可疑"——这个数字吓人但不可用，因为里面混着大量 `w3.org`、`schemas.openxmlformats.org` 这样的 XML 命名空间和文档链接，它们根本不是运行时调用的端点。

把规范命名空间、文档示例域、官方生态（github、skill 市场本身）归入白名单后，剩下 **275 处跨 141 个域名**需要人工复核——这才是合理的复核工作量。这里面绝大多数又是 `cdn.jsdelivr.net`、`arxiv.org` 这类无害引用，真正的收益是那几条孤零零的、说不清归属的域名：**它们才是要一条条点开看的**。

这是整个审计里我最想强调的判定哲学：**不要数 skill 数量，要看外发端点白名单。** 数量多不等于有问题，端点全部落在官方 API 和本地回环上，才是"通过"的定义。内网穿透隧道（trycloudflare）、短链接、公网 IP 直连——这三类出现任何一个，性质就完全不同了。

## 好消息：MCP 全过，而且和手工审计对上了

MCP server 审计（对照 OWASP MCP Security Guide 的五项判定：来源可信、无远程 MCP、鉴权、未使用即禁用、权限面）给我的 7 个 MCP server 给出了全绿的结论：全部本地进程或官方包，obsidian 这类 loopback 服务带 Bearer token，闲置的已禁用。

这个结论我可以背书，因为一个月前我手工做过同样一次审计，结论一致。**工具和人对上了**——这比工具本身多发现什么都重要：自动化审计的价值不是替代判断，是把"手工做过一次"变成"随时可以重跑"。

## 把流程变成工具

这次审计的完整流程就是开源的 [agent-audit](https://github.com/mo9652962-ai/agent-audit)：

```bash
pip install agent-env-audit        # PyPI 上线后可用
# 或直接从源码运行
pip install git+https://github.com/mo9652962-ai/agent-audit.git

agent-audit                        # 默认审计 Hermes 环境 + 当前工作区
agent-audit --checks ports,mcp     # 只跑指定检查
agent-audit --severity-threshold high   # 退出码可作 CI 门禁
```

设计上有三个坚持：**运行时零依赖**（安全工具先管好自己的供应链）、**全程只读**（修复命令写在报告里，由人决定是否执行）、**Windows 一等公民**（icacls/netstat/tasklist 直接支持——大部分同类工具默认 Linux，Windows 用户的 agent 环境根本没人管）。

报告输出 Markdown + JSON，包含一张"审计完成标准表"——6 条来自实战的验证标准逐条打勾，而不是一堆让读者自己下结论的原始数据。

## 现在就可以做的三件事

1. **跑一下** `netstat -ano | findstr LISTENING | findstr 0.0.0.0`，看看有几条你不认识的——那是你机器对局域网的全部敞口；
2. **grep 一遍记忆文件**：`grep -rn "sk-" ~/agent 的记忆目录`，命中真实 key 就移到配置文件里，原处只留位置说明；
3. **检查你的 MCP 配置**：有没有 `http(s)://` 开头且不是 127.0.0.1 的 server？有没有 npx 拉的、说不出出处的 npm 包？有就按[白皮书](../docs/mcp-security-audit-whitepaper.md)的五项清单过一遍。
